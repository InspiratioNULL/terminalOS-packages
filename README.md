# terminalOS packages

WebAssembly builds of real command-line tools for [terminalOS](https://github.com/InspiratioNULL/terminalOS),
with the source they were built from.

Each package is a `wasm32-wasip1` binary that terminalOS runs through wasm3,
the WebAssembly interpreter already embedded in the app. Installing one drops a
`.wasm` file into `~/Library/bin`; the shell finds it on `PATH` and runs it
under the bare command name, so `jq` is `jq`. A package installs one binary per
command it provides, which for every package here is one, except `nano`, which
also answers to `pico`.

| package | version | license | what it is |
|---|---|---|---|
| [`units`](src/units) | 2.23 | GPL-3.0-or-later | GNU unit converter, `units '15 mpg' 'km/l'`. The whole unit database is inside the binary. |
| [`jq`](src/jq) | 1.7.1 | MIT | JSON processor, with the regex builtins. Passes all 447 upstream tests under wasm3. |
| [`sqlite3`](src/sqlite) | 3.50.4 | public domain | The SQLite shell, with FTS5, R*Tree and JSON1. |
| [`datamash`](src/datamash) | 1.9 | GPL-3.0-or-later | GNU command-line statistics, `datamash -g 1 mean 2 sstdev 2`. |
| [`ed`](src/ed) | 1.21 | GPL-2.0-or-later | GNU ed, the standard editor. Scriptable, and needs no cursor addressing. |
| [`nano`](src/nano) | 9.2 | GPL-3.0-or-later | GNU nano, the full-screen editor, installed as `nano` and `pico`. Real ncurses, real syntax highlighting: all 39 definitions are compiled in. Needs character-at-a-time input enabled in the app, see below. |

Sizes are 138 KB (`ed`) to 1.3 MB (`nano`); the whole set is about 4.5 MB.
`nano` carries the same binary twice, once per name.

## Installing

    brew install jq
    brew search
    brew info units
    brew uninstall jq

`brew` reads [`index.json`](index.json), downloads `<name>.zip`, checks it
against the SHA-256 the index publishes, unpacks it into `~/Library/bin` and
keeps a receipt so the install can be undone. `brew update` refetches the
index; `brew outdated` and `brew upgrade` compare what is installed against it.
(`package` is a deprecated alias that forwards to `brew`.)

To install from a fork, a branch or a local file instead, point the shell at
another index:

    export TERMINALOS_BREW_INDEX=https://example.com/my-index.json

### The format a client can rely on

- **`index.json`** is generated by `tools/make-index.py`, so it never drifts
  from what is actually published. Each entry carries `name`, `version`,
  `description`, `homepage`, `license`, `commands`, `files`, `sha256`, `size`,
  `url` (absolute) and `archive` (relative to the index, for mirrors), plus
  `notes` for anything the user should know before running the thing.
- **`<name>.zip`** is an uncompressed tar despite the extension, holding a flat
  set of regular files with the executable bit set. No subdirectories, no
  compression, nothing above the archive root, terminalOS's `brew` refuses an
  archive that breaks any of those rules rather than unpacking it anyway.

## What these binaries can and cannot do

WASI is a small target, and wasm3's slice of it is smaller still. The limits
below are properties of the runtime, not of the individual tools, and they
apply to anything built this way:

- **Paths are relative to the working directory.** wasm3 preopens the shell's
  cwd and nothing else, so `jq . data.json` and `jq . sub/dir/data.json` work
  while `jq . /var/mobile/.../data.json` does not. `cd` first.
- **No subprocesses.** Nothing can shell out: no pagers, no `!command` in `ed`,
  no `.shell` in `sqlite3`, no `datamash decorate`.
- **No signals.** Ctrl-C cannot interrupt a running wasm program; it runs to
  completion.
- **No sockets.** Nothing here talks to the network: `socket`, `connect` and
  `gethostbyname` are not declared in wasi-libc, and WASI preview 1 has no
  call that opens a connection. wasm3 leaves `sock_send`/`sock_recv`/`sock_shutdown`
  commented out, and the shipped runtime exports no socket symbols. WebAssembly
  packages cannot fetch URLs; network access is handled via the app's native
  `curl`.
- **No timed waits.** `poll_oneoff` is not linked, and wasm3 refuses to *load*
  a module that imports one, so `poll`, `select` and every `sleep` are
  reimplemented in `tools/wasi_compat.c`. Sleeping is a busy-wait on the
  clock, capped at 250 ms, because there is no way to yield.
- **`ed` needs a writable working directory** for its buffer file. In a
  read-only directory it cannot open a buffer, so `cd ~` first.
- **`nano` requires character-at-a-time input from the app.** The shell buffers
  printable characters locally by default; when raw input forwarding is enabled
  for nano, keystrokes are forwarded directly. wasm3 reports fds 0-2 as a
  terminal, and the app exports `COLUMNS`, `LINES` and `TERM=xterm-color`.
- **`nano` cannot be suspended or resized.** ^Z reports a failure rather than
  backgrounding, because nothing can deliver a signal; for the same reason a
  rotate updates `COLUMNS` and `LINES` but no SIGWINCH arrives, so press ^L to
  redraw. ^T reports that it cannot run a command, and the spell checker,
  formatter and linter are not built. A lone ESC is not recognised until the
  next key arrives, since recognising it needs a timed wait; Meta combinations,
  where the two bytes arrive together, are unaffected.

## Building

Everything is built by `zig cc`, which cross-compiles C to `wasm32-wasi` and
carries its own wasi-libc:

    brew install zig lzip
    ./build-all.sh            # or ./build-all.sh jq

Each package is a directory under `src/` holding the pristine upstream tarball,
the patches applied to it, and a `build.sh` that goes from one to the other.
Nothing is vendored in modified form, so you can always see exactly what was
changed and why.

A few pieces of tooling make the rest work:

**`tools/wasi-cc`** is a C compiler that produces wasm binaries which are
runnable on the build machine: it compiles the link step to `<out>.wasm` and
leaves a shell stub at `<out>` that runs it through wasm3. An autotools
`configure` script normally answers dozens of questions by compiling and
running a test program, and gives up or guesses when cross compiling. Handed
this compiler it decides it is not cross compiling at all, and every runtime
answer comes from the engine the result will actually run on.

**`tools/build-wasm3-harness.sh`** builds terminalOS's own wasm3, the copy
vendored in the app repo, with its iOS code paths compiled in, as a macOS
binary. Packages are tested against that, not against wasmtime, because
wasmtime is more forgiving: SQLite built cleanly and ran fine under wasmtime
while failing every write under wasm3, which is the runtime that matters. Point it at
your terminalOS checkout:

    tools/build-wasm3-harness.sh /path/to/terminalOS
    tools/test-packages.sh

## Source and licenses

The GPL asks that the source for a binary be available from the same place as
the binary. It is: `<name>.zip` is built by `src/<name>/build.sh` from the
tarball in `src/<name>/upstream/` with the patches in `src/<name>/patches/`,
and that is the complete corresponding source. Nothing is fetched at build
time. The upstream tarballs carry their own `COPYING`.

The patches, build scripts and the glue in `tools/` are contributed under the
GPL-3.0-or-later as well, except `tools/wasi_compat.c` and
`tools/wasi_embed.h`, which are linked into programs of several licenses and so
are offered under the terms of whatever they are linked into.

## Adding a package

1. `mkdir -p src/<name>/{patches,upstream}` and drop the release tarball in.
2. Write `src/<name>/build.sh`, start from `src/jq/build.sh` for an autotools
   package, or `src/units/build.sh` for one you compile by hand.
3. Keep every source change as a patch in `patches/`, with a comment saying
   which WASI limitation forced it.
4. Add the package to `PACKAGES` in `tools/make-index.py`, a case to
   `tools/test-packages.sh`, and the name to `PACKAGES` in `build-all.sh`.
5. `./build-all.sh <name>` and check the tests pass.

Things worth knowing before you start:

- `setjmp`/`longjmp` needs WebAssembly exception handling, which wasm3 does not
  implement, so anything built around it (gawk, for one) will not work.
- macOS `ar` silently writes an empty archive from wasm objects, so pass
  `AR="zig ar"`.
- gnulib needs a few probes answered by hand, which `src/datamash/build.sh`
  documents one by one.
- If a package needs a library, build it the same way into a prefix under
  `build/` first; `src/nano/build.sh` does that with ncurses.
- Set `--build` and `--host` both to `wasm32-wasi`. Equal triples mean
  configure does not believe it is cross compiling, so it still runs its test
  programs, while `host_os = wasi` keeps it off the Darwin code paths
  `config.guess` would otherwise pick.
- Set `PKG_CONFIG=false`. macOS ships an `ncursesw.pc` that answers
  `-lncurses -D_DARWIN_C_SOURCE`, and a configure script that asks pkg-config
  first will happily try to link the host's native libraries into a wasm
  binary.
- Check the finished binary for imports wasm3 does not provide. The failure is
  at load time, before `main`, and says only which function was missing, not
  what pulled it in. `src/nano/build.sh` greps for `poll_oneoff`.
- Homebrew's `gnu-sed` shadows `/usr/bin/sed` on many Macs, and `sed -i ''` is
  a syntax error to GNU sed exactly as `sed -i` is to the BSD one. Use
  `edit_in_place` from `tools/common.sh`, which needs neither.
